# Статья для gmt-engineering.ru: от строки контент-плана до PR

Работаешь в репозитории `gmtossoriamkt/gmt-engineering`. Сайт статический, без сборки: GitHub Actions собирает из `main` чистую копию без служебных файлов (`scripts/build_dist.py`) и публикует её в ветку `timeweb-dist`, откуда Timeweb выкладывает сайт. Цель — достоверная статья в PR. **В `main` не коммитишь и не пушишь никогда**: публикация = merge PR владельцем. Workflow в `.github/` и деплой не меняешь.

## 0. Выбор задачи

1. Сначала переведи в `done` строки `content-plan.csv` со статусом `pr`, чьи статьи уже есть в `main` (папка `blog/<slug>/` в `origin/main`). Эти правки включи в PR текущей статьи.
2. Если в запросе указан номер — бери его. Иначе первую строку со статусом `todo` по порядку `num`, **пропуская темы, которые уже в работе**: статус в `main` меняется только после merge, поэтому сначала собери номера открытых PR и веток:
   `gh api "repos/gmtossoriamkt/gmt-engineering/pulls?state=open&per_page=100" --jq '.[].head.ref'` и `git ls-remote --heads origin 'blog/*'`. Номер из имени ветки `blog/<номер>-…` (или из заголовка PR `blog: <номер> …`) считается занятым — такую тему не бери, даже если в `content-plan.csv` у неё `todo`. Если ветка есть, а открытого PR нет (PR закрыт без merge) — тему тоже пропусти и упомяни в отчёте.
3. От свежего `origin/main` создай ветку `blog/<номер>-<короткий-слаг>`, поставь статус `in-progress`. Если сессия уже создала ветку с другим именем — работай в ней, номер статьи укажи в заголовке PR.
4. Если есть `factcheck/<номер>.md` — это фактчекинг редактора: учти его замечания, рекомендованный заголовок и структуру. Это тоже вторичный источник: его утверждения проверяются так же, как твои (в фактчекингах бывают устаревшие акты, неверные пункты и даты).
5. Если фактчекинга нет — сначала сделай его сам: какие режимы смешаны в теме (ТР ТС ≠ 102-ФЗ ≠ регистрация МИ), какие тезисы рискованны, какой заголовок не обещает лишнего.
6. Посмотри колонку `note` строки и уже опубликованные статьи по теме (`grep -ril "<ключ>" blog/`). Не повторяй их: дай новый угол и сошлись на них. Не противоречь им без причины; если нашёл ошибку в опубликованной статье — не правь её молча, а опиши в PR.

## 1. Исследование

- Первоисточники: тексты актов на consultant.ru, garant.ru (base.garant.ru), docs.cntd.ru, legalacts.ru; решения и техрегламенты ЕАЭС — docs.eaeunion.org / eec.eaeunion.org; метрология — fgis.gost.ru (Аршин), rst.gov.ru; аккредитация — fsa.gov.ru; медизделия — roszdravnadzor.gov.ru. pravo.gov.ru и government.ru из облака часто недоступны — не больше одной попытки.
- Сверяй **действующую редакцию** и срок действия акта на дату публикации. Учитывай известные переходы: приказ Минпромторга № 2905 (утверждение типа СИ) действует до 01.01.2027; ПП РФ № 1531 вступает в силу 01.03.2027. Проект акта — не действующее право: не цитируй его сроки как норму.
- Вторичные источники (обзоры, новости, сайты лабораторий) — только как подсказка. Факт, найденный только в них, подаётся мягко («по опубликованным обзорам…») или не подаётся.
- Цены: только из опубликованных прейскурантов с названием организации, датой проверки и оговоркой, что это цены одной организации. Своих цен и сроков ГМТ не придумывай — их нет в репозитории.
- Темы регистрации медизделий, ПП 719, ГИСП, реестров и госзакупок — это сайт med-local.ru. Здесь — угол разработчика прибора (что заложить в конструкцию, документацию, ПО), нормы кратко и ссылка на med-local.ru.

## 2. Текст

Структура (6 блоков, как во всех статьях блога):
1. **«Коротко»** (`<div class="summary"><strong>Коротко</strong>…</div>`) — 3–4 предложения, прямой ответ на интент: минимум одна цифра/срок/норматив, если они подтверждены.
2. **Нормативная база** — полные реквизиты актов (номер, дата, пункт), редакция.
3. **Маршрут / таблица / расчёт** — разделы H2 (`<h2 id="…">`), таблицы для сравнений, порядок действий или чек-лист.
4. **Кейс** — только реальный (с реквизитами) или с явной пометкой «условный пример».
5. **FAQ** — 4–6 вопросов; в теле место FAQ — строка `{FAQ}`, вопросы и ответы — в конфиге.
6. **CTA** (`<div class="cta">…<a class="btn btn-cta" href="/#contact">…</a></div>`) — по колонке `cta` плана, без обещаний результата.

Правила содержания:
- Каждый конкретный факт (номер пункта, дата, срок, порог, цена) — только если подтверждён первоисточником. Нет подтверждения — обобщи или убери.
- Практика ≠ норма: помечай «как правило», «на практике», «из практики разработки».
- Не обещай результат («пройдёте с первого раза», «сертификат не нужен») — пиши условия.
- Тон инженера-практика, без воды; русская типографика (« », —, неразрывные пробелы не обязательны).
- Объём — по колонке `volume` (±30%).
- Таблицы — только в `<div class="tbl"><table>…</table></div>`.
- Ссылки внутри сайта — относительные со слэшем: `/blog/<slug>/`, `/uslugi/…/`, `/marshrut/`, `/glossarij/`, `/stoimost/`.

## 3. Шаг 0 — сверка

Перед сборкой пройди по тексту и для каждого факта отметь: ✅ подтверждено (источник, пункт) / ✏️ исправлено (что было → что стало) / ❌ убрано (почему). Это отчёт для описания PR.

## 4. Сборка страницы

1. Конфиг статьи — Python-файл **вне репозитория** (например `/tmp/a<номер>.py`) со словарём `A`; поля описаны в `scripts/new_article.py`. Обязательно: `slug` (латиница через дефис), `title` ≤ 60 знаков с ключом, `desc` ≤ 155, `card`, `h1`, `crumb`, `rubric` (текст плашки — название рубрики, см. п. 4), `date` = сегодня, `date_ru`, `read`, `toc`, `related` (3 ссылки), `faq`, `body`, `cta_href`, `toc_btn`.
2. `python3 scripts/new_article.py /tmp/a<номер>.py` — страница собирается на шаблоне последней опубликованной статьи (шапка, MAX, меню, футер, cookie, Метрика — как на сайте). Руками шапку/подвал не правь.
3. `python3 scripts/og_cover.py <slug>` — обложка `assets/og/<slug>.png`. Открой её через Read и убедись, что заголовок помещается.
4. `python3 scripts/add_blog_card.py <slug> --tags "<рубрика>" --home-title "<короткий H1>" --home-desc "<одна строка>"` — карточка первой в блоге, первой в «Свежих статьях» на главной (третья уходит), sitemap. Рубрики (`--tags`, 1–2): `razrabotka` (железо, корпус, испытания; кластеры E, J), `po` (прошивки и ПО; F, G), `sert` (ТР ТС, метрология; A, B), `lokal` (реестры, госзакупки; C, D), `eaes` (ЕАЭС, экспорт; I), `otrasli` (H), `trendy` (K) — по содержанию статьи. Поле `rubric` в конфиге — **строго** название первой рубрики, как на кнопке фильтра блога: «Разработка и испытания», «Прошивки и ПО», «Сертификация и метрология», «Локализация и госзакупки», «ЕАЭС и экспорт», «Отрасли», «Тренды» (check_blog.py это проверяет).
5. Обратные ссылки: в «Смотрите также» (`.rel`) 1–2 профильных страниц услуг/направлений добавь ссылку на статью (формат — как у соседних ссылок) и обнови у них `lastmod` в `sitemap.xml`. Опубликованные статьи по смыслу не переписывай.
6. Если в статье новый термин — добавь его в `/glossarij/` (видимый `<dl class="gloss">` и `DefinedTermSet` в JSON-LD синхронно, ссылка на статью) и обнови счётчик терминов в description/тексте страницы.
7. Если меняешь содержание опубликованной статьи (факты, нормы): `dateModified` в JSON-LD, `lastmod` в sitemap и « · обновлено <дата>» в плашке даты. `datePublished` не трогай.

## 6. PR

1. В `content-plan.csv`: статус → `pr`, в `url` — `https://gmt-engineering.ru/blog/<slug>/`.
2. Коммит (автор — как в истории репозитория: `gmtossoriamkt <gmtossoriamkt@users.noreply.github.com>`), пуш ветки `blog/...`. Пуш рабочей ветки `blog/*` разрешён, в `main` — нет.
3. PR в `main` по шаблону `.github/pull_request_template.md`. `gh pr create` в облаке не работает (GraphQL закрыт) — открывай через REST:
   `gh api repos/gmtossoriamkt/gmt-engineering/pulls -f title='blog: <№> <тема>' -f head='blog/<ветка>' -f base='main' -f body="$(cat /tmp/pr-body.md)"` (черновик — добавь `-F draft=true`). Удалять ветки из сессии нельзя — не пытайся.
   В описании: адрес, title, description (с длиной), рубрика; отчёт шага 0; что осталось непроверенным и почему; изменённые файлы и страницы с обратными ссылками; адреса для переобхода в Яндекс.Вебмастере (статья, `/blog/`, главная, страницы с обратными ссылками).
4. В конце сессии — короткий итог со ссылкой на PR и краткий отчёт шага 0.

## Если что-то пошло не так

- Тема в плане юридически некорректна, а фактчекинга нет → пиши с исправленным заголовком и объясни в PR.
- Первоисточник по ключевому тезису недоступен, а смягчить тезис нельзя → открой PR как draft и пометь, что нужно решение человека.
- Тема дублирует опубликованную статью → не пиши дубль: поставь строке `skip` с причиной в `note`, возьми следующую `todo` и упомяни это в PR.
- Playwright/Chromium недоступен → статью собери, обложку и рендер-проверку не делай, открой PR как draft и напиши об этом.
- `main` ушёл вперёд, пока ты работал (в PR видно «This branch is out-of-date» или check_blog падает на шапке/подвале) → влей `origin/main` в свою ветку, пересобери статью `scripts/new_article.py` на свежем шаблоне и повтори проверки.
- Ничего не пушь в `main`, не меняй `.github/workflows/` и настройки деплоя.
